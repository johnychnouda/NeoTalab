# Architecture and development guide

How NeoTalab is built and how to work on it. Product and technical decisions are listed in [DECISIONS.md](DECISIONS.md).

## What this is

NeoTalab is a generic, multi-tenant "AI WhatsApp Commerce OS": WhatsApp is the merchant's storefront, an AI agent sells, and web dashboards manage the business. It must stay **business-type agnostic** (restaurants, pharmacies, retail, services…), so don't add vertical-specific assumptions to core code.

- `backend/`: Laravel 13 API (PHP 8.5), the only backend.
- `web/`: Next.js 16 / React 19 dashboards in plain JSX (no TypeScript), EN/AR/FR.
- `deploy/`, `docs/`: Railway runbook and release guides. Production is **Railway** (web + API + queue worker + MySQL); the web app is served at `https://neotalab.com` (DNS at Namecheap, `@` is an ALIAS to Railway; it must not be a CNAME, it breaks the TXT/MX records). The API is still on its `*.up.railway.app` domain.

## Commands

Backend (run from `backend/`):

```bash
composer install && cp .env.example .env && php artisan key:generate
php artisan migrate --seed          # local MySQL, db "neotalab"; owner from OWNER_EMAIL/OWNER_PASSWORD (generated + printed if empty)
php artisan serve --port=8001       # API (web's default API URL expects 8001)
php artisan queue:work              # required: WhatsApp webhooks are processed on the queue
php artisan test                    # in-memory SQLite, no MySQL needed (also: composer test)
php artisan test --filter=TenantIsolationTest          # single test class
php artisan test --filter=test_method_name             # single test method
./vendor/bin/pint                   # code style
php artisan schedule:work           # run scheduled commands locally (reports:daily, billing:remind, trials:expire, templates:sync, orders:due, backups)
php artisan owner:reset-password    # new platform-owner password + revoke all sessions (--email= if several owners, --new-email= to hand over)
```

Frontend (run from `web/`):

```bash
cp .env.example .env.local
npm install
npm run dev      # http://localhost:3001  (/owner, /backoffice)
npm run build
npm test         # Vitest: EN/AR/FR keys match, every t("key") exists, money/phone/revenue helpers
```

`composer dev` also exists but starts `serve` on the default port 8000, which the web app won't hit without overriding `NEXT_PUBLIC_API_URL`.

`NEXT_PUBLIC_API_URL` (in `web/.env.local`) defaults to `http://127.0.0.1:8001/api/v1` and is baked in at build time. Web tests live in `web/tests/` (no lint setup).

## Backend architecture

**Layering** (enforced convention): `Controller (Api\V1)` → `FormRequest` → `Service` (all business logic, constructor DI) → `Model` → `API Resource`. Controllers stay thin. All routes live in `routes/api.php` under `/api/v1`.

**Multi-tenancy**, single DB, row-level `merchant_id`. The tenant is the `merchants` table.
- `App\Support\CurrentTenant` is a request-scoped singleton holding the active merchant.
- `ResolveTenant` middleware (alias `tenant`, runs after `auth:sanctum`) binds it from the user's `merchant_id`.
- Models using the `BelongsToTenant` trait get `TenantScope` (auto `where merchant_id = ?`) and auto-filled `merchant_id` on create. **When no tenant is bound the scope is a no-op**: this is how platform super-admins see across tenants, and also means non-HTTP code (jobs, webhooks, console) must bind the tenant itself. See `WhatsAppInboundService::handle()` which `set()`s then `forget()`s in a `finally`.
- Every tenant-scoped table carries its own `merchant_id` (never derived via join). There are no DB-level foreign keys; child cleanup is done explicitly in service transactions.
- Use `newQueryWithoutTenancy()` only for deliberate cross-tenant/system queries.

**Auth / RBAC**, Sanctum bearer tokens (expire after `SANCTUM_EXPIRATION`, default 30 days); no public self-registration; merchants are created via `/join` approval or the owner portal. Named rate limiters (`login`, `onboarding`, `api`) live in `AppServiceProvider::boot()`; spatie/laravel-permission roles (constants in `App\Support\Roles`): `platform-super-admin` (merchant_id null), `merchant-owner`, `merchant-admin`, `merchant-staff`, `driver` (reserved). Routes gate with the custom `role:` middleware (`EnsureRole`), typically `$merchantRoles` for reads and `$managerRoles` (owner+admin) for writes. `/admin/*` is super-admin only. Audit via spatie/laravel-activitylog.

**IDs & DB**, UUID primary keys (`HasUuids`, `char(36)` in MySQL). Keep migrations DB-agnostic since tests run on SQLite and prod on MySQL.

**AI conversation engine**, `App\Services\AI\Contracts\ChatProvider` with `FakeChatProvider` (default, deterministic, used in tests) and `OpenAiCompatibleChatProvider` (`AI_DRIVER=openai`, JSON-schema structured output). Each turn gets a `shop` context (name, currency, hours, delivery zones) and only the last `ai.conversation.history_turns` messages; catalogs bigger than `ai.catalog.full_max` are cut to the items matching the customer's recent words (`CatalogSearch`, `shop.catalog_is_partial`); conversations idle longer than `ai.conversation.idle_hours` are closed and their cart abandoned. Checkout: when the AI returns `recommended_action=place_order` with a `checkout` object, `ConversationService` calls `CheckoutService::placeOrder()`, which re-validates everything (cart, opening hours in the merchant's timezone, delivery zone, address, zone minimum, stock) and either creates the order or throws a `CheckoutException` whose translation key becomes the customer reply. The AI never sets prices, fees or availability. `processTurn()` returns `reply`; always send that, not `output->assistantMessage`. Customer-facing WhatsApp texts live in `lang/{en,ar,fr}/whatsapp.php`; order status changes queue `NotifyCustomerOfOrderStatus` (only when the status actually changes), assignment queues `NotifyDriverOfAssignment`, and checkout queues a delayed `CheckLateOrder`. These jobs share `Jobs\Concerns\SendsMerchantWhatsApp`, which binds the merchant and restores the previous tenant (on the sync queue they run inside the HTTP request). `OrderService::notify()` swallows dispatch failures, since a WhatsApp problem must never fail the merchant's action. Meta only allows free-form messages within 24h of the recipient's last message, so drivers stay inside it by messaging "start"; owner messages (nightly report, billing reminder) go from the shop's own number to the owner's personal number using per-shop Utility templates that `ShopTemplateService` submits on connect and `templates:sync` refreshes hourly. Until a template is approved they go as plain text only when the owner's number wrote to the shop number in the last 24h (`StaffMessenger::numberInWindow`); otherwise they are skipped with a warning (Owner → Inbox → System), since Meta accepts and silently drops plain text outside the window. The report number can't be the shop's own number. A 1–3 rating alerts staff inside the window (else the report number inside the window); the customer is promised a follow-up only when someone was told. The Team API returns `reachable` per member, and the Team page tells the owner which staff must send "hi" first. The OpenAI JSON schema must stay valid for strict mode (every property required, `additionalProperties: false`); `CheckoutTest` enforces this. The fake driver understands `confirm | zone | address | payment | currency` for tests. Never parse free-form model text; output is mapped to DTOs (`StructuredTurnOutput`, `CartAction`, …) and applied by `ConversationService` / `CartService` / `CatalogResolver`. Config in `config/ai.php`.

**WhatsApp flow**, Meta hits `POST /api/v1/webhooks/whatsapp` → `ProcessWhatsAppWebhook` job → `WhatsAppInboundService` resolves the merchant by `phone_number_id` (`MerchantWhatsAppCredentials`), binds the tenant, runs the conversation turn, replies via `WhatsAppService`. All `entry[]`/`changes[]` in a payload are processed; the unique `(merchant_id, wa_message_id)` index is the idempotency guard, so a job retry never reprocesses a message. AI/send failures are caught per message and answered with a fallback text instead. Several queue workers run side by side (`backend/docker/queue.sh`), so `processMessage()` holds a `Cache::lock` per merchant + customer number: one chat is answered one message at a time, in order, while other chats run in parallel. In production the webhook rejects everything if `WHATSAPP_APP_SECRET` is unset. Credentials model: one platform access token (in `platform_settings`) plus per-merchant phone ID in `merchants.settings.bot`; a merchant-level `access_token` overrides. Access tokens in settings JSON are stored encrypted with APP_KEY through `App\Support\StoredSecret` (`open()` still reads older plain values), so never read them raw. A number that floods a shop (`whatsapp.customer_limit_per_10_minutes` / `_per_day`) gets no AI reply, so spam cannot run up the AI bill. Embedded Signup onboarding is in `WhatsAppEmbeddedSignupService` / `web/components/owner/WhatsAppEmbeddedSignup.jsx`.

**Tests**, real environment variables (including values from your local `backend/.env`) override config in tests unless `phpunit.xml` pins them; any env-driven secret a test depends on (e.g. `WHATSAPP_PLATFORM_ACCESS_TOKEN`) must be pinned there. Feature tests use `Tests\Concerns\InteractsWithTenants` (`merchantWithUser()`, `platformAdmin()`, `tokenFor()`). New tenant-scoped features should come with isolation and RBAC tests following the existing `*IsolationTest` / `*RbacTest` pattern.

**WhatsApp-only operations** (see [DECISIONS.md](DECISIONS.md)): the merchant never works orders in the dashboard. `WhatsAppInboundService::processMessage()` routes each inbound message: registered driver number → `DriverBotService` (start/stop, `drv:picked_up:{id}` / `drv:delivered:{id}` button ids); customer whose chat is paused (`customers.bot_paused_until`: the merchant sent ⏸ from the WhatsApp Business app (seen as `message_echoes`), or the bot handed the chat to staff) → ignored; lone 1–5 after a rating request → rating; otherwise the AI. Voice notes are downloaded (`WhatsAppService::downloadMedia`), transcribed through the `SpeechToText` contract (`OpenAiSpeechToText`, `gpt-4o-mini-transcribe`, menu names as a hint; `FakeSpeechToText` reads `ai.speech.fake_transcript` in tests) and then handled like typed text; photos/stickers/videos/files, and voice notes that can't be heard, get a polite note plus the menu list, so a customer is never left without a reply. Photos/videos/files pause the bot in that chat and alert the staff (`NotifyStaffOfHandoff` reason `photo`) when a staff member can be reached; otherwise the note + menu. Appointments: products with `duration_mins` are bookable services (never cart items). `AppointmentService` computes free slots from shop hours (default 09:00–18:00), `appointment_capacity` and `slot_step_mins` in the shop timezone (DB stores UTC); the AI returns `check_availability` / `book_appointment` / `cancel_appointment` with an `appointment` object and the server writes the replies. Whish Pay: `WhishPayService` (per-merchant channel/secret in `settings.whish`, secret encrypted) creates a payment link; A Whish order is always `placed` first and gets its payment link only once the shop accepts (`OrderConfirmation::accept()` → `startWhishPayment()`), so a refused order is never paid: staff tap Accept, or (the usual case: one shop phone, no staff) whoever holds the shop phone types ✅ (or ❌) in the customer's chat, read from `message_echoes` by `WhatsAppInboundService::answerFromShopPhone()`. The bot never accepts a Whish order by itself; reminders go to the customer's chat. Whish orders stay `pending_payment` until `OrderConfirmation::settleWhish()` verifies the status with Whish (signed `whish.callback` route, plus `CheckWhishPayment` jobs during and at the end of `wish_timeout_mins`); callbacks are never trusted alone. The money goes straight to the shop's own Whish business account (Whish Pay channel + secret). `OrderConfirmation::afterConfirmed()` is the single place that dispatches drivers, staff and the late timer. Team members live in `drivers` with `role` = `driver` (assigned deliveries, start/stop shifts) or `staff` (every new order with Ready/Collected or Out for delivery/Delivered buttons via `NotifyStaffOfOrder`, `open`/`close` sets `settings.mode`, handoff alerts with a resume button). Staff messages go through `StaffMessenger`: interactive buttons inside the 24h window (last inbound from that number in `whatsapp_messages`), else the approved `neotalab_new_order` / `neotalab_staff_alert` template whose quick replies come back as `type: button` with `button.payload` = the button id. Shops with staff accept orders themselves (Accept / Can't take it); when no staff member can be reached, `needsShopAcceptance()` is false and the bot accepts, and `NotifyStaffOfOrder` accepts too if no ticket went out. Orders have `fulfillment` = `delivery` | `pickup` from the shop's `ShopSettings::fulfillment()` (delivery/pickup/both); pickup orders skip zone/address/fee and are never dispatched. `CheckoutService` creates orders already `confirmed`; `DriverDispatcher` assigns the on-duty driver free the longest and re-dispatches waiting orders when a driver frees up. Operational settings live in `merchants.settings`, read through `App\Support\ShopSettings`. Delayed jobs (`CheckLateOrder`, `RequestOrderRating`) run instantly on the sync queue, so tests `Bus::fake()` them and call `handle()` explicitly. Problem alerts: `AppServiceProvider` listens to `MessageLogged`, so every warning/error the app logs goes through `SystemAlertService` into `system_alerts` (one row per problem, with a count; secrets stripped) shown in Owner portal → Inbox → System; errors also email/WhatsApp the recipients in `platform_settings.settings.alert_email|alert_whatsapp` (WhatsApp uses the `system_alert` template on the platform number). Recording is guarded so it can never break or loop on the caller. `trials:expire` (every 15 min, `TrialExpiryService`) suspends shops whose free trial ended unpaid. A suspended shop's number is ignored by `findMerchantByPhoneId`, so it costs nothing until marked paid. `reports:daily` runs hourly; the scheduler loop is started in the background by `backend/docker/entrypoint.sh` on the API service (`RUN_SCHEDULER`), not a separate Railway service. The scheduler also writes a heartbeat every minute; `LaunchChecklistService` (`GET /admin/system-status`, shown at the top of Inbox → System) uses it together with the AI, WhatsApp, queue, email, alert and backup settings to show what is still missing on the server. The API is served by FrankenPHP (`backend/Dockerfile`), and `trustProxies('*')` makes Railway's forwarded IP and https count.

## Frontend architecture

- Next.js App Router. Dashboard pages are client components (`"use client"`); the public pages (`/`, `/privacy`, `/terms`) are server components exporting `metadata`. They are what Meta reviewers check for business/app verification (business identity, contact details, data-handling and deletion info), so keep them accurate and reachable without login. Three app surfaces: `/owner` (platform super-admin portal), `/backoffice/[shop]` (merchant **setup** dashboard: opens on Get started; no orders page by design), `/join` (public merchant onboarding application; **Lebanon only for now**; open countries are `ENABLED` in `web/lib/countries.js` and `App\Support\Countries`, which also sets a new shop's timezone and currency on approval). Dashboard prices go through `formatMoney(value, shop.currency)` (`web/lib/money.js`). Merchants use it on phones: check layouts at ~375px width.
- Never render user-controlled strings as HTML (`ConfirmModal` takes a React node as `message`; shop names come from the public `/join` form).
- `web/lib/api.js` is the single API client: `apiFetch(role, method, path, body)` with separate localStorage tokens per role (`owner` / `merchant`). `path` is the real `/api/v1` route (e.g. `/settings/profile`, `/admin/merchants`) and `body` is sent as is, in the field names the backend validates. `normalizeResponse()` unwraps the Laravel `{data: …}` envelope and reshapes a few responses (lists under a named key, `normalizeMerchant`); add response shaping there rather than in pages. No demo-mode fallback; errors surface.
- i18n: `web/lib/i18n.js` (`LangProvider` / `useLang`) holds EN/AR/FR strings; AR requires RTL-safe layout. Add new UI strings in all three languages.
- `@/` path alias maps to `web/` (`jsconfig.json`).
