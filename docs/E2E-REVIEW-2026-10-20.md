## 3. Real problems (fix these)

### 3.1 Staff are not told when a customer cancels an order (high)
When a customer cancels before the shop accepts, the customer gets "cancelled", but the shop
never hears. The staff member still sees **Accept / Can't take it** and can accept it.
Result: an order can be prepared for a customer who left.
*Test:* 20b. *Fix:* send the staff the cancellation and remove the buttons from the ticket.

### 3.2 A customer who types "checkout" with no delivery choice is stuck (medium–high)
Typing "checkout" (or "confirm") before choosing delivery or pickup gets the plain sentence
"Would you like delivery or will you pick up the order from the shop?" with **no buttons**.
Typing "delivery" then gets "Sorry, I did not understand." The button flow works, so the
problem only hits customers who type instead of tapping.
*Test:* 21c. *Note:* the typed answer depends on the stand-in AI, so the second half may
behave differently with the real AI. The missing buttons are a real problem either way.
*Fix:* always answer with the Delivery / Pickup buttons.

### 3.3 Owner gets "unknown phone number" alerts for a suspended shop (medium)
When a shop's trial has ended and it is suspended, its number is ignored on purpose (it costs
nothing). But every message to it is logged as "WhatsApp inbound: unknown phone_number_id",
which becomes a warning the owner sees in Inbox → System. The owner sees a false alarm, and
the message is misleading (the number is not unknown, the shop is suspended).
*Evidence:* `MerchantWhatsAppCredentials::findMerchantByPhoneId` filters out suspended shops, so
they look unknown. *Fix:* detect "suspended" and log that, or stay quiet.

### 3.4 A photo, then a sticker: silence (low–medium)
After a customer sends a photo, the chat is paused for staff. A sticker sent next gets no
reply at all. The platform's own notes say a customer is "never left without a reply". This
is probably intended while a person handles the chat, but the promise and the behaviour do not
match. *Test:* 24. *Fix:* either tell the customer "a team member will answer", or update the note.

## 4. Things that work but need an owner decision or a clearer screen

1. **Daily report and reminders need the owner to write to the shop first (medium).** The
   report to the owner's personal number is skipped until that number has messaged the shop
   in the last 24 hours (Meta drops anything else silently). The skip is only logged as a
   warning. Most owners will never write first, so they will simply get no report, and nothing
   tells them. *Test:* 34. *Decision:* ask owners at onboarding to send "hi" to the shop number,
   or send reports from the platform number instead.
2. **Menu import shows the lira price as dollars in the preview (medium).** A row written as
   "250,000 LL" shows **250000** in the dollar column before you press Import, but it is saved
   as **2.79$**. The owner sees one number and gets another. *Evidence:* seen while testing the
   preview (not a saved check). *Fix:* show the converted value in the preview.
3. **Google Maps links are sent to customers (policy).** The pickup receipt ("🏪 Pickup at
   https://www.google.com/maps?q=…") and the booking confirmation contain map links. The
   written decisions say no links go to customers except Whish. Decide which is right, then
   align the code or the decision.
4. **API ignores wrong field names but still answers 200 (low).** When the owner portal's
   price change sent `subscriptionPrice` (a wrong name), the server replied success, saved
   nothing, and the public price stayed at 30$. The web app sends the right names, so
   real users are not affected, but a future bug would be silent.
5. **Wording: "1 items" / "1 articles" (low).** The cart line uses the plural for one item in
   all three languages (`items_count` / `added` strings). French was seen directly.
6. **Zone names in customer messages (low).** Customers see "Up to 6 km" (in French and
   Arabic sentences too). Zones could show the area name instead.

## 7. Limits of this test (what was NOT proven)

- **Whish payments** (customer pays by Whish, and the subscription payment): the Whish servers
  are hard-coded in the code, so a real or sandbox Whish payment cannot be run here. The
  Whish-related unit tests pass in the suite, but nothing end-to-end.
- **Meta / WhatsApp**: templates were not approved by Meta, so every message that needs an
  approved template (new order to staff outside the 24-hour window, the owner's report) was
  tested through the fallback paths only. Real delivery was not tested.
- **The AI**: the stand-in AI understands only fixed phrases. Real free-text ordering, real
  Arabic/French understanding, and the language the AI detects were not tested. Customer
  language was set directly in the database for the Arabic and French customers.
- **Voice notes**: only the "can't hear it" path was tested; real transcription was not.
- **Travel time**: fixed times per zone were used, not Google's driving times.
- **Overnight hours** (Friday 11 AM to 2 AM): covered by the unit tests, not in this run.
- **Timeouts**: the 10-minute "no answer" rule was triggered by running the job directly, not
  by waiting.
- **Whish subscription work** (branch `claude/goofy-bhabha-4337a6`, commit `5e9a194`): not
  merged, not tested here.
- Browser checks used stored login tokens to open the dashboards quickly. The login screens
  themselves were tested earlier today.
- Widths between the ones listed, and the 1280 px desktop width, were not run separately.
