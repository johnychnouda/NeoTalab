## Finding while writing the browser tests
- The login is rate limited. Repeated sign-ins in quick succession show "Too Many Attempts". This is intended protection. The browser tests now sign in once per account and reuse the session.

## Phase E/F: concurrency and a full pickup journey
Script: `scratchpad/qa/journey_concurrency.py` (lab API and lab database only; not stored in the repository because it depends on the lab's test data).

Journey tested through the WhatsApp webhook: customer orders falafel for pickup, pays cash, staff taps Accept six times at the same moment, then Ready, then Collected, then the closed order is refused Refuse, Ready and a second Collected.

Result: **12 passed, 0 failed.**
- Six simultaneous Accept taps: the order is confirmed once, `accepted_at` is set once, the customer gets at most one confirmation message.
- Refusing an accepted order is refused. After delivery, Refuse, Ready and Collect again change nothing.
- The run created exactly one order for the customer.

Corrections made while writing the journey (test-side, not product defects):
- A first version expected "Collected" to be refused before "Ready". The code allows it on purpose (`OrderService::delivered()` accepts confirmed orders because drivers and staff often skip steps), so the expectation was wrong.
- A check that counted all of a customer's orders failed after the script ran twice. It now counts only the orders created by that run.
- A check that always passed was rewritten as a real assertion.

Not covered yet: a delivery journey with a driver (the existing WhatsApp suite covers it, phases 14 to 29, but this run did not repeat it), real rollback after a database error, and concurrent edits in the shop dashboard.

## The items that were still not covered
1. **Simultaneous settings saves** (`scratchpad/qa/concurrent_settings.py`, lab API and database): two shop-dashboard saves at the same moment, each changing a different setting (shop name and preparation time), repeated 25 times. Both changes were kept in all 25 runs. Result: **1 passed (25 races)**.
   - An earlier run of the same script reported 401 errors. Those were login rate-limit failures, not lost updates. The script now refuses to count a run unless both saves return 200, and it waits before its single sign-in.
2. **Rollback after a database error** (`backend/tests/Feature/ProvisioningRollbackTest.php`): creating a shop and its owner login is one transaction. A failed owner step (email already taken) leaves no shop behind. A successful one creates both together. Result: **2 passed**. This test is new; before it, no test in the repository covered rollback.
3. **Full delivery with a driver** (`scratchpad/qa/journey_delivery.py`, lab WhatsApp flow): order with a map pin → staff accepts → handed to the on-duty driver → picked up → delivered → driver free → delivery count +1 → total matches the quote → shift ends → the shift-end message states the same cash the database holds for that shift. Result: **10 passed, 0 failed**.
4. **Real WhatsApp, Whish and Google checks**: not run. Each one sends a real message, moves real money, or makes a paid external request. They need your approval per action.
