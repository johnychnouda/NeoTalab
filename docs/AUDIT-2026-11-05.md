# NeoTalab audit, 5 November 2026 (delta round)

## Verdict

**CONDITIONALLY READY**, unchanged from 3 November. Today's code passes every lab suite, every page in three languages on five browsers and sizes, and 300 real-assistant conversations (290 fully right, no invented price, no mixing between shops). Railway with production's 40 workers answers about 12 customer messages a second with replies in 4 to 6 s; 80 workers double that. Four problems were found and fixed (a security update, D54, D55, and test mistakes). What still keeps this conditional cannot be done from here: real Meta at volume, real payments, the real OpenAI API at peak rate, and an outside security test.

This round re-tested everything that changed after the full audit of 3 November (`docs/FINAL-REPORT-2026-11-03.md`) and closed some of its gaps. It does not repeat the parts of that audit that the new code does not touch. All work is on branch `qa/delta-audit-2026-11-05`. Nothing is on `main` or production yet.

## Observations (not fixed, on purpose)

- **A stopped shop can still edit its menu in the dashboard.** What it pays for (the WhatsApp assistant) is off on the server. Keeping the dashboard open lets it see what is due and stay ready. Say if you want it read-only.
- **Arabizi customers get the bot's own buttons in English.** This is in the code on purpose (Latin letters). The assistant itself answers in Arabizi.
- **A customer who sends a second message before the first reply** may get two location reminders in a row. The behaviour is correct; it is just one extra message.
- **The forwarded-address header** (D17): sign-in limits no longer depend on it. Railway has still not confirmed which header is safe.

### Railway capacity with an assistant as slow as the real one (T21)

Setup: a temporary Railway project (`loyal-youthfulness`, US West, Hobby plan), separate from production, built from the throwaway branch `scale-test-temp`: today's code plus a fake Meta route and a fake assistant that holds the worker 1.5 to 4.5 s per message, like gpt-6-luna. The real OpenAI key was not used: I may not type keys into Railway, and the question is how many customers the workers can serve while each waits on the AI, which the wait answers. Secrets were generated by Railway. Data: a copy of the laptop lab (126 shops, 54,220 orders, 26,537 customers). Queue: 40 workers, as in production. Load from the laptop in Lebanon through the signed webhook (70% customers) and the dashboard (30% owners), `qa/s45_railway_load.py`. Railway showed a network incident banner during the test.

| Users at once | Customer messages a second | First reply: typical / slowest 5% | Errors | Customers never answered |
|---|---|---|---|---|
| 10 | about 4.6 | 3.8 s / 5.6 s | 0 | 0 |
| 25 | about 11.7 | 4.2 s / 5.6 s | 0 | 0 |
| 50 | about 22.6 | 28 s / 50 s | 0 | 0 |
| 100 | about 46 | 84 s / 156 s | 0 | 0 |

- **40 workers answer about 12 messages a second** (40 workers ÷ about 3.2 s each). Below that the reply comes in 4 to 6 s; above it the queue grows and replies wait, but nothing is lost or refused.
- The webhook and dashboard stayed fast at every level (p95 under 0.8 s from Lebanon to California).
- Peak use at 100 users: queue 0.75 vCPU and 2 GB, MySQL 0.6 vCPU and 1 GB, API 1 vCPU and 120 MB. The machines were mostly idle: the limit is the number of workers waiting on the AI, not CPU.

Same test with **80 workers**:

| Users at once | First reply with 40 workers | First reply with 80 workers |
|---|---|---|
| 50 | 28 s / 50 s | **3.9 s / 5.6 s** |
| 100 | 84 s / 156 s | 30 s / 51 s |

Workers scale in a straight line: 40 answer about 12 messages a second, 80 about 25. Each worker costs about 50 MB of memory.

**What this means for the business.** 120 shops at 600 messages a shop a day is about 1 message a second on average, maybe 10 a second at the busiest hour, which today's 40 workers carry with replies in 4 to 6 s. Raise to 80 workers (about +$8 a month of memory) once shops together pass about 8 messages a second at peak; the queue wait in Owner → Inbox → System is the sign. Not measured: the real OpenAI API at this rate (its own rate limits), real Meta, and several hours in a row.
